## Problem Statement

In 51 real runs on Chalk 0.7.x (#7, #85), no loop ever failed its rubric. When an agent could not make progress, it reported `blocked`. That happened 4 times, and every one was real and cheap:

| Run | Spent before blocking | Blocker | What the human did |
|---|---|---|---|
| PY-3 | $0.11 | `import yaml` fails; the image has no pip | added python3-yaml to the image |
| GO-5 | $0.14 | `go test -race`: `cgo: C compiler "gcc" not found`, no sudo | added gcc and libc6-dev to the image |
| NODE-4 | $0.30 | 60 ms perf budget unreachable under jest GC | raised the budget to 100 ms in the spec |
| NODE-4 | $0.25 | 100 ms still failed 1 in 5 | raised it to 150 ms |

Each blocker cost one detention and a human session of office hours. Three things went wrong:

1. **You investigated what the agent already knew.** The agent named the exact fix in its blocker text every time, but `run_detain` printed a generic `next:` line ("provide what the agent asked for above").
2. **The lessons learned the wrong thing.** Distillation wrote "report missing gcc as a blocker", not "this repo needs gcc in its image". The cause is `share/prompts/distill.md` itself: its third example teaches "report a blocker asking for the registry token to be rotated" (lines 48-52), and `office_hours_fix` describes every fix made outside the repository the same way.
3. **The decider never ran.** The stuck-loop verdicts and the shadow decider got zero data, because the case they target, a loop failing its rubric, never happened. Blockers did.

## What Makes This Cool

Every blocker arrives with **its own proof and its own fix**. The agent's blocked answer carries a probe: a command that fails now and must pass once the blocker is fixed, such as `gcc --version` or `python3 -c 'import yaml'`. The same probe:

- proves the blocker is real, with no model involved;
- checks that the fix worked before Chalk keeps it as a lesson;
- becomes a saved need in `.chalk/needs` (what the repo needs from its environment), which pre-flight, `chalk doctor` and CI can run, so the same gap is never paid for twice.

A human intervention leaves something that can be run, not just prose.

## Constraints

- Bash 5.3 harness, `docs/bash-style.md` rules; every external program has a fake in `tests/fakes/`.
- The sandbox runs as a non-root user with no sudo. Image fixes cannot happen inside a run.
- Chalk owns exactly one Dockerfile, `share/sandbox/Dockerfile` in the install. It is not in the user's repo. When `CHALK_IMAGE` is a custom image, Chalk never builds it (`sandbox_ensure_image` stops with "pull or build it first").
- The decider acts only after the calibration gate (#36: ≥20 judged answers, ≥90% right, per URL and model revision). Until then every decider question here runs in shadow mode.
- Open source, solo, part-time. Each PR must be useful on its own.

## Premises

Agreed during the session, with premise 3 revised after the second opinion:

1. **Optimise human turnaround, not agent spend.** Blockers cost cents; your time is the expensive part.
2. **The agent proposes, you approve.** The blocked answer carries a structured fix. Chalk shows it at detention and applies it only on `chalk office-hours --accept`, never on its own.
3. **Rules sort first, and the decider's main job is lesson matching.** Text rules sort blockers by kind; we expect them to sort all 4 recorded blockers correctly, and PR 2's tests check that against the recorded texts. The decider answers "does past lesson X already answer this blocker?" for each recalled lesson. The 6-way sort and "would a retry with a hint get past it?" also run in shadow; they will be slow to calibrate at about one blocker per 13 runs.
4. **An accepted fix becomes the lesson,** scoped to the repo. When its kind is environment-shaped (image, config), its probe becomes a saved need.
5. **In scope, staged:** the retryable judgement, a pre-flight before loop 1 (#48), and environment needs declared as config.

## Recommended Approach: B, then C

The ladder handles a blocker by trying the cheapest, surest step first:

1. **Proof:** run the agent's probe; it should fail.
2. **Rules:** sort the blocker by kind from its text.
3. **Lessons:** does a past fix already answer it? (decider, shadow)
4. **You, with a ready fix:** detention shows the fix; `--accept` applies spec and config fixes and resumes.
5. **Pre-flight:** before later runs, saved needs are checked before loop 1, so a known gap costs no loop spend.

### The fix the agent proposes

`CHALK_SCHEMA[loop]` (`lib/agent.sh`) gains an optional `fix` object. `blocker` stays as the free text.

| Field | Meaning |
|---|---|
| `kind` | `image`, `spec`, `config`, `credential` or `decision`. `retryable` is not an agent kind; it is a judgement made by the decider and recorded as an outcome. |
| `why` | One or two sentences, with the evidence (the error line, the measurement). |
| `patch` | Only for `spec`: a unified diff that may touch `specs/$TICKET.md` and nothing else. |
| `config` | Only for `config`: an object of `.chalk/config` keys to new values, for example `{"CHALK_SETUP_CMD": "…"}`. Only keys in `CHALK_CONFIG_DEFAULTS` are accepted. `.chalk/config` is in the committed tree the sandbox clones, so the agent can read it. |
| `image` | Only for `image`: the packages or lines a Dockerfile needs (for example `apt-get install -y gcc libc6-dev`). Shown, never applied. |
| `probe` | Only for `image` and `config`: a command that fails now and passes once the environment is fixed. Spec, credential and decision fixes have no probe: a spec change proves itself when the agent meets the new spec, and the sandbox holds no credentials to check. |

A blocked answer without `fix`, or with a `fix` that fails these rules, detains exactly as today, with the free text, and the problem is logged.

### Probe outcomes

`run_probe` runs the probe through `sandbox_sh` with a 30 s timeout and records the exit code and the first 2000 characters of output:

- **failed** (non-zero exit other than below): evidence the blocker is real.
- **passed** (exit 0): shown as "the probe passes, so this blocker may not be real". The run is still detained; nothing acts on it automatically.
- **inconclusive**: timeout (124), the command not starting (126, 127 for the probe's own shell), or a harness error. No claim is made.

A probe runs once. A flaky check (NODE-4's perf budget failed 1 in 5) is a spec fix with no probe, so flakiness does not reach this step. The "read-only" rule in the prompt is advice, not a guarantee, so the probe runs after the detention commit (`sandbox_commit` in `run_detain`), and its writes never reach the detention branch.

### Where blockers are stored

The `blockers` table is the source of truth for `--accept`, `--retry` and the report card. `$RUN_IO` is wiped by the next run of the ticket, so nothing depends on files there.

| Column | Set by |
|---|---|
| `id`, `run_id`, `repo`, `ticket`, `branch` (detention branch), `detained_at` | PR 1, at detention |
| `fix` (jsonb: the agent's whole `fix`), `kind_agent` | PR 1 |
| `probe_outcome` (`failed`, `passed`, `inconclusive`, null if no probe), `probe_exit`, `probe_output` | PR 1 |
| `kind_rule` | PR 2 |
| `outcome` (`accepted`, `manual`, `retried`), `resolved_at`, `lesson_id` | PR 2, at office hours |
| `kind_human` | PR 2: an explicit confirmation in office hours (one key, defaulting to `kind_rule`, skippable). Unconfirmed rows are never used to calibrate. |
| `retry_result` (`passed`, `blocked_again`, `failed`) | PR 2, when the resumed run ends |

### PR 1: Blockers carry proof and a fix (`feat(run)`)

- **`share/prompts/distill.md`:** replace the registry-token example with a fix-shaped one ("When `go test -race` reports gcc not found, this repo's sandbox image needs gcc and libc6-dev."). Add the rule: when the note or the fix describes a fix, the lesson states the fix, not the act of reporting.
- **Distill inputs:** with zero commits, `<fix_diff>` says "no code change; the fix was outside the repository, described in the engineer's note" (the note itself still goes in `<engineer_note>`, not twice). An accepted structured fix goes in as its own `<accepted_fix>` input.
- **`share/prompts/system.md`, `continue.md`:** when blocked, propose `fix` per the table above.
- **`lib/run.sh`:**
  - `run_detain blocked` records the `blockers` row, runs the probe after the detention commit, and shows the fix and the probe outcome.
  - `run_next_step blocked` prints a line per kind. For image fixes it names the step for both cases: with the default image, "build a repo image `FROM chalk-sandbox:local` that adds these packages and set `CHALK_IMAGE`"; with a custom `CHALK_IMAGE`, "add these packages to the image you build as `CHALK_IMAGE`".
  - The closing hint lists `-m`, and later `--accept` and `--retry` when they apply.
- **Ejected prompts:** repos with their own `.chalk/prompts/distill.md`, `system.md` or `continue.md` keep the old text. `chalk doctor` warns when an ejected copy of these three lacks the new rule, and the release notes say so.
- **Done when:**
  - e2e (fake claude) cases: a blocked answer with a fix (probe fails), one whose probe passes, one whose probe times out, and one with no fix (today's detention).
  - The 4 recorded notes, replayed through the new distill prompt, give lessons that each name the missing package or the new budget and contain no "report a blocker" wording.

### PR 2: Rules, `--accept` and `--retry` (`feat(lifecycle)`)

- **`lib/blocker.sh`** (new): `blocker_kind TEXT -> REPLY` reads the blocker text only. First match wins:

  | Order | Pattern (extended regex, case-insensitive, anchored on the error phrase) | Kind |
  |---|---|---|
  | 1 | `C compiler .* not found`, `: command not found$`, `executable file not found in \$PATH` | image |
  | 2 | `No module named '[^']+'` or `Cannot find module '[^.][^']*'` where the module is not a path inside the repo | image |
  | 3 | `(401\|403) (Unauthorized\|Forbidden)`, `authentication required`, `token (expired\|invalid\|missing)` | credential |
  | 4 | `(budget\|threshold\|limit) .*(unreachable\|cannot be met\|too (low\|tight))` | spec |
  | — | nothing matches | `decision` |

  Unit tests run it on the 4 recorded texts (expected: image, image, spec, spec) and on negative cases: a missing repo module, a parser "unexpected token", a line number next to "not found".
- **`chalk office-hours --accept`:** reads the newest unresolved `blockers` row for the ticket and shows the full fix. Then, by kind:
  - `spec`: refuses if the patch touches anything except `specs/$TICKET.md`; otherwise `git apply`, show the diff, commit on the detention branch.
  - `config`: refuses keys outside `CHALK_CONFIG_DEFAULTS`; otherwise writes the values to `.chalk/config` and commits.
  - `image`, `credential`, `decision`: refuses, and prints the manual step from PR 1.

  For `config` with a probe, it then starts a fresh sandbox on the detention branch, runs `CHALK_SETUP_CMD` (the possibly updated one), then the probe. If the probe does not pass, the commit stays and you get the output, but no lesson is kept and the run does not resume. This costs one sandbox start (seconds) and no agent spend. Then it resumes as office hours does today. A patch that does not apply, or a row with no fix, falls back to the `-m` flow with a clear message.
- **`chalk office-hours -m` after a manual image fix:** the same fresh-sandbox probe check. If it passes, it offers to save the probe as a need.
- **`chalk office-hours --retry -m "hint"`:** resumes with the hint, sets `outcome=retried`; `retry_result` is set when the resumed run ends.
- **Saved needs:** a new file, `.chalk/needs`, with one line per need: `probe command  # ticket, lesson id`. The line format is what `load_config` can't hold (one `KEY=value` per line). A need is saved only when you confirm it during an accept or a manual fix, shown verbatim. Only image and config fixes produce needs.
- **The lesson** stores the accepted fix next to the distilled text.
- **Done when:** e2e covers spec accept, a spec patch touching other paths (refused), config accept with the probe passing and failing, an image refusal with the right manual step for both image cases, a patch that does not apply, `--retry`, and saving a need.

### PR 3: The decider on blockers, in shadow (`feat(decider)`)

Uses what is already on main: `decider_ask`, the `decisions` table, and #36's per-URL calibration gate.

- **Lesson match (main job):** candidates come from today's recall on the blocker text (lexical, then semantic where Postgres 17 has vectors), up to `DECIDER_SHORTLIST`. A blocked loop has no fingerprint, so there is no exact-fingerprint stage. For each candidate, a `noul` question: "Does this past fix resolve this blocker?". Judged right if you accepted or applied that lesson's fix (`blockers.lesson_id`).
- **Model-free match:** a lesson whose saved need is the same probe command (after trimming whitespace) as the new blocker's probe is shown at detention as "a past fix that may answer this", with no model needed.
- **Sort and retryable (shadow):** a `choice` question over the five kinds, judged against `kind_human`, and a `noul` "Would a retry with this hint get past it?", judged against `retry_result`. Both are built now because they are two more prompts on the same call path (no new infrastructure), and every blocker from here on becomes a labelled example. Neither may act until it passes the gate, which may take a long time.
- **The report card** gains a blocker panel: blockers by kind, probe outcomes, accepted fixes, minutes from `detained_at` to `resolved_at`, and the decider's shadow accuracy per question, with an explanation when it is empty (as in #87).
- **Done when:** decisions are recorded for every blocker with at least one recalled lesson, and the panel renders.

### PR 4: Pre-flight before loop 1 (`feat(run)`, closes #48)

- **Setup:** a failing `CHALK_SETUP_CMD` now detains (new kind `preflight`) instead of stopping with `die`, so the run ends in a resumable state.
- **Saved needs:** after setup, run each `.chalk/needs` probe in the sandbox. A failure detains as `preflight` with a `next:` line naming the need, its ticket and the lesson that added it.
- **Rubric baseline:** run `CHALK_TEST_CMD` once before loop 1 and record it. This is record-only at first, because a test-first spec fails at the start by design (including "No module named" for code the agent has not written). The only failure that detains is exit 126 or 127 (the rubric's own command cannot run).
- **#48's question:** "does this checkpoint need network, secrets or a human decision?", asked in shadow per checkpoint after pre-flight passes, judged against whether that checkpoint later blocked with kind `credential` or `decision`. It is a local model call, not agent spend.
- **`chalk doctor --needs`** runs `.chalk/needs` inside the sandbox image. CI runs it the same way, inside the image, never on the runner itself.
- **Done when:** a run against an image without gcc, with `gcc --version` in `.chalk/needs`, detains in pre-flight with no loop spend; a test-first spec does not detain.

### Then C: devcontainer as the environment's source of truth (under #29)

- If the repo has `.devcontainer/devcontainer.json`, Chalk builds that image first and adds a thin layer on top: the claude CLI, bash 5.2 and the non-root agent user.
- Image fixes then propose a patch to `devcontainer.json` (a feature, or an install step). `--accept` can apply it: patch, rebuild, re-run the probe, resume.
- Repos without a devcontainer keep B's behaviour (image fixes shown, applied by hand).
- C gets its own design pass under #29 (stack images) once B has shipped. Open choices there: the `devcontainer` CLI (Node) or a bash subset of the format, build caching, and how it combines with `CHALK_IMAGE`.

## Success Criteria

- The next real blocker shows its proposed fix, the probe outcome and a kind-specific `next:` line at detention.
- Lessons from office hours state fixes: the 4 recorded notes replay into lessons that name the package or budget, with no "report a blocker" wording.
- A spec or config blocker goes from detention to resumed with one `--accept`, and a config fix's probe passes in a fresh sandbox before the lesson is kept.
- A saved need catches a known environment gap in pre-flight with no loop spend.
- The decider has recorded shadow answers on real blockers (#85 resolved for blockers), and the report card explains its numbers.

## Reviewer Concerns

### R2-1 — feasibility

**Problem**

> Probe outcomes classify exit 127 'for the probe's own shell' as inconclusive. The design's own example probe `gcc --version`, run through `sandbox_sh` (a shell) in an image without gcc, exits 127 from that shell with 'command not found'. So the motivating GO-5 blocker, and any 'tool is missing' image blocker, would be reported as inconclusive instead of failed, and no proof is shown. The phrase 'the probe's own shell' does not define how a 127 from the missing tool differs from a 127 from the harness (for example docker exec failing to start the shell).

**Remedy**

> Treat a 126/127 returned by the probe command as failed (a missing or non-executable tool is the blocker), and reserve inconclusive for timeout (124) and harness errors detected outside the command (container not running, sandbox_sh itself failing). Add an e2e case with a probe for a missing binary.

### R2-2 — consistency

**Problem**

> PR 4 says a saved need's probe 'failure detains as preflight', but the probe outcome rules define three outcomes. It is not stated whether a need that times out or returns 124/126/127 detains, warns or is skipped. Saved needs are mostly 'is the tool present' checks, which fail with 127, so the mapping decides whether pre-flight works at all.

**Remedy**

> State the pre-flight mapping for each probe outcome (failed and missing-tool detain; timeout and harness error detain or warn, chosen explicitly), using the same classification as detention, and test both.

### R2-3 — clarity

**Problem**

> blocker_kind 'reads the blocker text only', but rule 2 applies only 'where the module is not a path inside the repo'. From text alone, `No module named 'yaml'` (PY-3, image) cannot be told apart from `No module named 'mypkg'` for repo code the agent has not written, yet a 'missing repo module' is listed as a negative test case. The inputs of the rule and the negative test contradict each other (the R1-6 obligation to state each rule's inputs is unmet for this rule).

**Remedy**

> Either give blocker_kind the repo tree (and define the check, for example the top-level module name matching a directory or file in the repo, or a relative path in `Cannot find module`), or drop the repo-module condition and the matching negative test and accept that rule's false positive.

### R2-4 — feasibility

**Problem**

> The rule table uses `: command not found$` and says patterns are case-insensitive and 'anchored on the error phrase'. Bash `[[ =~ ]]` matches the whole blocker text as one string with no multiline mode, so `$` matches only at the end of the whole free text, and case-insensitivity needs `nocasematch`. The rule would miss the error in any multi-line blocker.

**Remedy**

> Specify that blocker_kind matches line by line (or drop the `$`), and that it sets case-insensitive matching locally, consistent with docs/bash-style.md. Cover a multi-line blocker in the unit tests.

### R2-5 — consistency

**Problem**

> Premise 3 now presents the 4-of-4 sort as an expectation, but the Cross-Model Perspective still states 'rules already get 4 of 4' and the closing coaching section says the decider weight moved 'once the data showed rules already sort today's blockers'. No rule output on the recorded texts is shown, and the second NODE-4 blocker as summarised ('100 ms still failed 1 in 5') contains none of rule 4's words (unreachable, cannot be met, too low/tight), so it may fall to the `decision` default.

**Remedy**

> Reword the remaining claims as expectations, or show the rule table's output on the 4 recorded blocker texts (quoting the texts) before relying on it.

### R2-6 — completeness

**Problem**

> A config fix may set any key in CHALK_CONFIG_DEFAULTS. That list includes CHALK_TEST_CMD (the rubric), CHALK_PERMISSION_MODE (bypass), CHALK_BUDGET_USD, CHALK_MAX_LOOPS, CHALK_REVIEW, CHALK_SPEC_CHECK and CHALK_IMAGE. An agent stuck on its rubric could propose weakening the rubric or the review as a 'config' fix, and `--accept` would commit it. The R1-10 obligation to restrict config fixes to allow-listed keys is unmet.

**Remedy**

> Define a short allow-list for agent config fixes (for example CHALK_SETUP_CMD and CHALK_RUBRIC_TIMEOUT), refuse every other key at --accept, and show the before and after values of each key.

### R2-7 — clarity

**Problem**

> load_config gives the environment precedence over .chalk/config. If the key a config fix changes (for example CHALK_SETUP_CMD) is set in the environment, --accept writes the file, but the fresh-sandbox probe and the resumed run still use the environment value. The probe result would then not reflect the accepted fix.

**Remedy**

> State that --accept checks for an environment override of each changed key and refuses (or warns and stops) when one is set, and test it.

### R2-8 — completeness

**Problem**

> The config --accept probe check is binary ('if the probe does not pass'). It does not say what happens when CHALK_SETUP_CMD fails in the fresh sandbox or the probe is inconclusive, or what state the blockers row is left in after a failed check (the commit stays, nothing resumes). A second --accept would re-apply an already-committed change; it is not defined whether that is idempotent, refused, or whether the user must switch to -m.

**Remedy**

> Define the outcome for setup failure and inconclusive probes at accept, the row state after a failed check (still unresolved, with the attempt recorded), and the next step printed (re-run --accept to re-probe without re-committing, or -m).

### R2-9 — completeness

**Problem**

> `chalk office-hours -m` after a manual image fix runs the fresh-sandbox probe and 'if it passes, offers to save the probe as a need'. It is not said whether the run resumes when the probe fails or is inconclusive, nor where the new CHALK_IMAGE comes from in that check (an environment variable, or a .chalk/config change that must be committed on the detention branch first).

**Remedy**

> Specify -m's behaviour for each probe outcome (for example warn and ask before resuming on failure), and state that a CHALK_IMAGE change is read from the committed .chalk/config or the environment for the check and the resumed run.

### R2-10 — feasibility

**Problem**

> Saving a need writes `.chalk/needs`, but the design does not say that the file is committed, or on which branch. The sandbox clones the committed tree, so an uncommitted needs file is invisible to pre-flight, and a dirty tree blocks the next run (run_context requires a clean tree). Needs saved on a detention branch also reach the base branch only if that branch merges.

**Remedy**

> State that a confirmed need is committed to `.chalk/needs` on the detention branch together with the fix, and that it reaches later tickets through the normal merge, or choose another committed location.

### R2-11 — clarity

**Problem**

> The `.chalk/needs` line format `probe command  # ticket, lesson id` is ambiguous when a probe itself contains `#` (a URL fragment, a shell comment, `${#var}`). The parsing rule and what happens to a malformed line are not defined.

**Remedy**

> Define the separator parse (for example split on the last `  # `), reject probes that would be ambiguous when saving, and say that pre-flight warns on and skips malformed lines.

### R2-12 — completeness

**Problem**

> PR 4 adds a `preflight` detention kind, but it has no blockers row, no agent fix and no loop commit. The design does not say how it is resolved: whether `-m` re-runs setup and the failing need, whether --accept and --retry apply, what branch the detention uses, or whether it is recorded in the report card.

**Remedy**

> Specify the preflight detention's resume path (fix the image or setup, then `-m`, which re-runs pre-flight before loop 1), which office-hours flags apply, and whether a row is recorded.

### R2-13 — consistency

**Problem**

> PR 3 judges the lesson-match answer 'right if you accepted or applied that lesson's fix (blockers.lesson_id)', but blockers.lesson_id is set 'at office hours' and reads as the lesson produced by this blocker's resolution, not the past lesson whose fix was reused. Nothing records which recalled lesson, if any, actually answered the blocker, so the main decider job has no label source.

**Remedy**

> Add a separate column (for example `matched_lesson_id`, set when the human confirms that a shown past fix answered it) and judge the match question against that, keeping lesson_id for the new lesson.

### R2-14 — consistency

**Problem**

> kind_human is a one-key confirmation that defaults to kind_rule. A human pressing through the default produces a label equal to the rule output, so the sort question's calibration measures agreement with the rules rather than the human's judgement, the same bias R1-16 removed for the agent's kind.

**Remedy**

> Record whether the human changed or merely accepted the default, or require an explicit choice without a preselected kind, and state which rows count for calibration.

### R2-15 — scope

**Problem**

> PR 3 still builds the sort and retryable shadow questions now.
