## Problem Statement

Chalk pays for, or guesses at, decisions that are bounded and repetitive. Two of them cost the most:

1. **Is this loop stuck?**
   - `lib/run.sh:364-378` counts every loop that made no progress, and sends the run to detention after `CHALK_MAX_RETRIES`+1 of them in a row. At the defaults that is three loops at up to $1.00 each.
   - The counter cannot tell "the same assertion failed and the tree is identical" (stuck) from "7 failing tests went down to 2" (converging).
   - **v1 addresses only the first half: it stops stuck runs earlier.** Converging runs are still detained at the counter limit (Premise 5). v1 records every `improving`-then-detained run in the ledger as evidence for a possible v2.
2. **Which past lessons apply to this failure?**
   - Recall is either `pg_trgm` similarity > 0.1 with the top 3 kept (`lib/db.sh:113`), or Hindsight, which needs a 2 GB container plus an LLM API key (`lib/memory.sh`).
   - Both match on noisy text. A lesson's `signature` is the detention reason plus 40 raw log lines (`run.sh:208-215`). The recall query is the whole spec, or the reason plus 60 raw log lines (`run.sh:116`).
   - Trigram similarity over raw test-runner output mostly matches runner boilerplate. It also can't see paraphrases, such as `ECONNREFUSED` versus `connection refused`.

User's framing: "improve sandbox to rely less on llm or add system 1 local models", pointing at [strands-labs/strands-decider](https://github.com/strands-labs/strands-decider):
- It is a 2B decision model: a Qwen3.5-2B torso plus a pointer head.
- It answers yes/no (`noul`), `choice` and `score` questions in one forward pass, at about 150 ms warm on an M3 Pro.
- `noul` answers are calibrated: at ≥ 0.9 confidence they are right about 95% of the time.
- It serves `/v1/systemone` over HTTP, takes many questions about one text in a single request, and is Apache-2.0.

## What Makes This Cool

- **Chalk already has its own source of truth.** Most agent harnesses detect stuck loops by hashing tool calls, because they never run the tests themselves. Chalk runs them every loop. Fingerprinting the rubric's output and the working tree catches the plain cases with no model at all.
- **The model only handles the gray zone.** The local model is used only where the rules can't decide, and acts only above a calibrated confidence threshold. Everything else still goes to Claude.
- **Every decision is measured in dollars.** Shadow mode records where each rule or the model *would* have stopped, what the later loops cost, and how often it would have been wrong.
- **Recall gets a complete ladder:**
  1. exact fingerprint match;
  2. lexical similarity;
  3. semantic similarity (pgvector embeddings);
  4. a calibrated rerank by the decider.

  Each step is cheaper than the one after it, and each later step switches on only when there is enough data for it to help.
- **Hindsight is removed** on cost and complexity grounds. Whether the new recall matches its quality is measured, not assumed.

## Constraints

- **Runtime:** Chalk is bash 5.3 on the host and bash 5.2 in the sandbox, and follows `docs/bash-style.md`. It has no Python dependency today. `uv` becomes an *optional* dependency, used only by the host service in PR 3b.
- **Where the models run:** the decider and the embedding model run on the **host**, because MLX cannot reach the Mac GPU from inside Docker. Supported backends are MLX (Apple silicon), CUDA, MPS and CPU.
- **Optional, never blocking:** the host service never blocks a run. When it is down, not installed or slow, Chalk behaves exactly as it does with `CHALK_DECIDER=off`.
- **Test output:** `CHALK_TEST_CMD` is arbitrary bash, so the output format is unknown in general.
- **Tests:** the e2e suite runs on fake `docker`, `claude`, `gh` and `glab`, so the host service needs a fake too.
- **Data volume:** there are still few real runs, so the `lessons` table is small.
- **Database:** `chalk-db` runs `postgres:16-alpine` today (`lib/db.sh:21`). PR 3a moves it to Postgres 17 with pgvector. That is a major-version upgrade, and it also switches from musl to glibc.
- **The ceiling on savings at the defaults:** `CHALK_MAX_RETRIES=2`, so a run is detained on its third failing loop in a row.
  - `repeat` or `no_change` can fire on the second failing loop at the earliest, which saves at most **one loop (≤ $1.00) per detention**.
  - `deja_vu` is checked before `first`, so it can fire on the first failing loop and save up to two.
  - The savings grow for users who raise `CHALK_MAX_RETRIES`.

## Premises

1. **Rules come before models.** Stuck detection starts from deterministic fingerprints. The decider only judges loops the rules cannot classify.
2. **The models run in one optional host service.** `chalk decider up` installs it via `uv` and runs it on 127.0.0.1, serving the decider and a small embedding model. It never runs inside the sandbox, and the Homebrew formula does not depend on it.
3. **Hindsight is removed (revised after the second opinion).** Recall becomes a ladder:
   - exact fingerprint match;
   - then lexical similarity on the normalized first error;
   - then, once there are enough resolved lessons, semantic similarity (pgvector) and a decider rerank.
4. **Shadow mode comes first.** `CHALK_FP_RULES=off|shadow|on` (default `shadow`) and `CHALK_DECIDER=off|shadow|on` (default `off` until installed). In shadow mode a decision is recorded and costed but changes nothing: not the loop's outcome, and not its prompt.
5. **v1 can only stop runs earlier, never spend more.** A verdict can send a run to detention sooner. It can never grant loops beyond `CHALK_MAX_RETRIES`.

## Approaches Considered

### Approach A: Fingerprints only (System 0)
Not chosen on its own, because it leaves the System 1 goal unmet. It became PRs 1 and 2.

### Approach B: Full decision ladder (chosen)
Fingerprints, then lexical, semantic and decider recall, and the decider for gray-zone stuck loops. Everything is shadowed and costed.

### Approach C: Pluggable judge, with Chalk evaluating itself
Every bounded question answered by `rules|decider|haiku`, all shadowed. Rejected for now: it builds an abstraction before there is data to justify it, and shadowing Haiku spends tokens on every question. Revisit once the ledger exists.

### Test reports: why XML

JUnit XML is the only report format most runners share: pytest `--junitxml` (built in), `go-junit-report`, `jest-junit`, cargo-nextest, Maven Surefire and Gradle. Their JSON outputs each use their own schema, and go and jest can both emit JUnit through `go-junit-report` and `jest-junit`. So `CHALK_TEST_REPORT` (a path inside the repo) must be JUnit XML:

- **JUnit XML:** a constrained awk reads `<testcase ...>` elements that contain a `<failure` or `<error` child, taking `classname` + `name`.
- **JSON readers** (`go test -json`, `jest --json`) are **deferred** (eng review D1). Add them if the ledger shows go or jest repos with mostly `UNKNOWN` test sets.
- **Anything else** is `UNKNOWN`.

The harness deletes the report inside the sandbox before each rubric run, so a stale report is never read. After the run it reads the report with `docker exec cat`.

### Fingerprints (defined once, used by all PRs)

Computed in `lib/fingerprint.sh` after a rubric run, and **before** any commit that run.sh makes for that loop.

- **T, the failing test set.** A sorted, unique list of test IDs, or `UNKNOWN`.
  - It comes from the report when `CHALK_TEST_REPORT` is set and readable. Otherwise it comes from a regex over `rubric.log`: pytest `FAILED a::b`, go `--- FAIL: X`, cargo `test x ... FAILED`, jest `● Suite › test`.
  - An empty match is `UNKNOWN`, never "zero failures".
- **E, the normalized first error.** The first line matching an error pattern (`error`, `Error:`, `FAIL`, `panic`, `Traceback`, `assert`), with ANSI codes, hex addresses, `:line:col`, temporary paths, timestamps and durations stripped. Empty if nothing matches.
  - **E is *generic*** when it consists only of a runner banner, for example go `FAIL <pkg>`, `npm ERR! Test failed`, a bare `error:`, or `N failed`. These come from a small denylist with a fixture per entry.
- **D, the working-tree identity.** This is a tree ID, not a diff, so it doesn't depend on `RUN_BASE`. Inside the sandbox:

  ```sh
  cp .git/index .git/chalk-fp-index
  GIT_INDEX_FILE=.git/chalk-fp-index git add -A -- . ':(exclude)specs/*.notes.md'
  D=$(GIT_INDEX_FILE=.git/chalk-fp-index git write-tree)
  ```

  - Copying the real index keeps git's stat cache, so a large repo isn't fully rehashed.
  - The index lives under `.git/`, so it never appears in the tree.
  - Untracked, non-ignored files are included.
  - **The notes file is excluded**, because `retry.md` and `continue.md` tell the agent to update it every loop. Otherwise a stuck agent that follows instructions would change D on every loop.
  - "Unchanged" means the same tree ID as the baseline loop.
- **The lesson fingerprint.** sha256 of (T joined, E), but only when T is known or E is non-empty and not generic; otherwise NULL.

### Verdicts

A **streak** is the run of consecutive non-progress loops since the last progressing loop, or since the run started. The **baseline** is the most recent loop in the current streak that has a fingerprint. Every non-progress loop gets exactly one verdict:

| Why the loop didn't progress | Verdict |
|---|---|
| Agent reported `blocked` (detains at once today, `run.sh:330`) | `blocked`, no fingerprint |
| Agent stopped early (CLI error, budget) | `agent_error`, no fingerprint, today's counter. It doesn't become a baseline. |
| Rubric passed, no checkpoint ticked | D only: `no_change` if D equals the baseline's D, `first` if there is no baseline, otherwise `other` |
| Rubric failed | Compute T, E and D, then the first matching rule below wins |

The rules for a rubric failure, in order:

1. `deja_vu`: T is known, and the lesson fingerprint matches an *open* lesson for another ticket in the same repo created in the last 30 days. This needs no baseline, so it can fire on the first loop.
2. `first`: there is no baseline.
3. `repeat`: D is unchanged, and either T is unchanged and known, or T is `UNKNOWN` on both loops and E is unchanged, non-empty and not generic.
4. `no_change`: D is unchanged.
5. `improving`: T is known on both loops and has fewer entries now.
6. `spinning`: T is unchanged and known, or T is `UNKNOWN` and E is unchanged, non-empty and not generic.
7. `other`: anything else.

**What each mode does:**

- **`CHALK_FP_RULES=on`:** `deja_vu`, `repeat` and `no_change` send the run to detention immediately, with the verdict as the reason. All other verdicts only record, and leave today's counter in charge.
- **`shadow`:** everything is computed and recorded, and nothing is acted on.
- **`off`:** nothing is computed or recorded, and the decider's gray-zone question is disabled too, since it depends on verdicts. The decider's recall steps still work.

### Lessons and detention

`run_detain` gains two optional arguments, the fingerprint and E. It passes them to `db_open_lesson REPO TICKET SIGNATURE RUN_ID [FINGERPRINT] [FIRST_ERROR]`.

- They are set **only** when the detaining loop was a rubric failure. They come from that loop's fingerprint.
- Lessons for blocker, final-review, loop-limit and `agent_error` detentions get NULL for both.
- NULL and empty values are excluded from exact match and `deja_vu`.

### PR 1: Verdicts and the ledger (no change to agent behaviour in shadow mode)

- **`lib/fingerprint.sh`**, with bats fixtures for:
  - real pytest, go, jest and cargo failures;
  - a build error with no tests (expect `UNKNOWN`);
  - an unknown runner;
  - a stale report;
  - a new untracked file (expect a different D);
  - a change to the notes file only (expect the same D);
  - two passed-no-tick loops in a row;
  - the sequence `agent_error`, fail, fail;
  - two tickets that share only a generic E (expect no `deja_vu`).
- **`run.sh`:** compute the fingerprint (`fp_compute`) and the deja_vu lookup before `sandbox_commit`, then call `fp_verdict REASON PREV CUR -> REPLY`. That function lives in `lib/fingerprint.sh`, does no I/O, and is covered row by row by `tests/unit/fingerprint_test.sh` (eng review Q1, D9). All of this sits behind `CHALK_FP_RULES`. **The retry feedback and the recall query are unchanged.**
- **Schema** (all via `ADD COLUMN IF NOT EXISTS`):
  - `runs`: `run_id`, `tests_hash`, `failing INT` (NULL when unknown), `first_error`, `tree_id` and `verdict`.
  - `lessons`: `run_id`, `fingerprint` and `first_error`, with a btree index on `(repo, fingerprint)`.
  - `run_id` is generated once at run start as `$RUN_TICKET-$EPOCHSECONDS`. `lessons.run_id` is the link between a detention and its run (detention branch names are unrelated).
- **Ledger** (`dashboard.sql`, per `run_id`):
  - *Would have saved:* the cost of loops after the first stopping verdict in detained runs, split by verdict.
  - *False stops:* a stopping verdict followed by a loop that progressed, shown next to the savings with the cost of that later progress.
  - *Converging but detained:* runs detained after an `improving` verdict.
- **"Notes for next term":** suggest `CHALK_FP_RULES=on` when the bar in Success Criteria is met. Suggest `CHALK_TEST_REPORT` when T is `UNKNOWN` for most loops in a repo.

### PR 2: Fingerprint recall and Hindsight removal

- **Recall order**, with up to 3 lessons in total. Exact matches come first and are never displaced.
  1. Exact match: non-NULL `fingerprint`, resolved, same repo.
  2. Lexical, across repos (as today):
     - After a failure, `similarity(first_error, E)`, falling back to `signature` similarity for older lessons with no `first_error`.
     - **Before the first loop**, the query is the spec, matched with `word_similarity(lesson_text, spec)` against `coalesce(first_error, signature)`. Plain `similarity` against a one-line error would almost never clear 0.1, which would make first-loop recall vanish.
- **Recall input is separate from prompt feedback.** It is E plus T after a failure, and the spec before the first loop.
- **The retry feedback change** (normalized T and E plus a 20-line tail) ships behind `CHALK_FP_FEEDBACK`, **default `false`** in this release. The recall change gets a clean measurement window, and the feedback default flips in a later release once loops-to-progress has been compared. The flag's value is part of the `run_prompts_version` hash, so the existing by_prompts panel compares the two modes (eng review S5, D5).
- **Hindsight cleanup:**
  - Delete the Hindsight code in `memory.sh`, plus `db_unsynced_lessons` and `db_mark_lesson_synced`.
  - Keep the `memory_synced_at` column, with a schema comment saying why.
  - `CHALK_MEMORY=hindsight` and the `CHALK_MEMORY_URL`, `_BANK`, `_TOKENS` and `_IMAGE` keys are accepted, ignored and warned about once.
  - `chalk memory` prints a removal notice with `docker rm -f chalk-memory && docker volume rm chalk-memory-data`.
  - The CHANGELOG repeats this, and warns users with an external `CHALK_MEMORY_URL` that it is no longer used.
  - Remove the keys from the config template and the README.

### PR 3a: Postgres 17 with pgvector

- **New installs** use `pgvector/pgvector:pg17`. `schema.sql` adds `CREATE EXTENSION IF NOT EXISTS vector`, guarded so a pg16 database simply skips it.
- **`db_up` picks the image that matches the volume** (eng review A2, D6):
  - An existing `chalk-db` container is started as-is. If it is still on 16, `db_up` warns once ("run `chalk db upgrade`; semantic recall is off until then") and carries on. A run is never blocked.
  - If the container is missing, and the legacy `chalk-db-data` volume exists with no `chalk-db-data-17`, it recreates a pg16 container on the legacy volume.
  - Otherwise it creates pg17 on `chalk-db-data-17`.
  - pg17 is never started on pg16 data.
- **`chalk db upgrade`:**
  1. Refuse if any runs are active.
  2. `pg_dumpall` from the old container.
  3. Stop the old container and rename it `chalk-db-16`.
  4. Create a new `chalk-db` on the new image with the **new** volume `chalk-db-data-17`, and restore the dump into it.
  5. Verify row counts for `runs`, `events` and `lessons`.
  6. **On any failure in steps 3-5:** remove the new container and the `-17` volume, rename `chalk-db-16` back to `chalk-db`, and start it.
  7. Keep `chalk-db-16` and its volume until `chalk db upgrade --cleanup`.

  Restoring the dump rebuilds every index under glibc, which takes care of the musl-to-glibc collation change.
- **Host profile and locking (eng review TD3, D13):** a new `lib/core/system.sh`.
  - `system_profile` fills `SYS[os cores ram_mb docker_mem_mb docker_cpus has_flock]` once per process.
    - Host RAM comes from `sysctl -n hw.memsize` on macOS, or `/proc/meminfo` on Linux.
    - Cores come from `getconf _NPROCESSORS_ONLN`.
    - Docker comes from `docker info --format '{{.MemTotal}} {{.NCPU}}'`.
    - `has_flock` comes from `command -v flock`.
    - A probe that fails leaves its key unset, and every consumer falls back to today's fixed value.
  - **`chalk_lock NAME`** uses `flock` when available and an atomic `mkdir` otherwise (stock macOS has no flock). A lock whose pid is dead is cleared. `decider_start_once` (A3) and db_up's create branch both use it.
    - db_up re-checks for the container after acquiring the lock.
    - It treats "name already in use" as "created elsewhere" and waits for `pg_isready`.
    - This fixes the pre-existing race where the first fleet launch on a fresh machine fails with "could not start: database".
  - **Adaptive timeouts:** the db ready wait (today 30 s) and the decider and chalk-embed ready waits double when `docker_cpus < 4`, when `docker_mem_mb < 4096`, or on a container's first initialisation. `CHALK_*_TIMEOUT` keys still override.
  - **`CHALK_MAX_PARALLEL=auto`** (new default; an explicit number still wins). It resolves to the smallest of:
    - 8;
    - `docker_cpus / 2`;
    - `(docker_mem_mb - 1024) / CHALK_SANDBOX_MEM_MB`, where `CHALK_SANDBOX_MEM_MB` defaults to 2048.

    The result is at least 1. If the profile is unknown, it falls back to 4.
  - **Regression contract (eng review T2, D14):**
    - config.sh accepts only `auto` or a positive integer; anything else dies with a message.
    - `fleet_parallel -> REPLY` resolves the value before the arithmetic at `fleet.sh:112`.
    - Explicit integers are used as-is, and the e2e §3 fleet test is unchanged.
    - Tests: `config_test.sh:30` expects `auto`, and a unit table pins 6→6, unknown→4, (8217 MB, 12 CPU)→3, (32768 MB, 16 CPU)→8, and invalid→die.
  - `chalk doctor` prints the profile and the resolved values.
- **Tests:** `make test-db` runs against pg17, plus an upgrade test from a pg16 fixture volume. The e2e suite (fake docker) covers a successful upgrade, a restore failure that rolls back, and a missing container on the legacy volume.

### PR 3b: The host service (decider and embeddings)

- **`lib/decider.sh`**, modelled on `memory.sh`:
  - `chalk decider up|down|status`.
  - `up` checks for `uv` (failing with an install hint if it's missing), runs `uv tool install strands-decider==<pinned>`, and **downloads** the pinned decider model (v19) and a pinned small embedding model (384 to 1024 dimensions).
  - It then starts the service on 127.0.0.1 with a pidfile under `~/.local/state/chalk/`. Embeddings are served by `share/decider/chalk-embed.py`, a single file with PEP 723 inline metadata pinning its dependencies and model. It is started with `uv run --script` next to `strands-decider serve`, managed by the same `up`/`down`, and serves OpenAI-compatible `POST /v1/embeddings` plus `GET /health` on 127.0.0.1. It ships in the existing Homebrew tarball (eng review A1, D8).
  - `chalk doctor` lists `uv`, the service and both models as optional.
- **Lifecycle:**
  - When the service is installed and `CHALK_DECIDER` is not `off`, `run_start_services` starts it **fire-and-forget** through `decider_start_once`. It is not added to `jobs_wait`, and it never downloads anything during `chalk run`.
  - `decider_start_once` takes an atomic `mkdir ~/.local/state/chalk/decider.lock`, so concurrent fleet runs start exactly one copy. A lock whose pid is dead is cleared (eng review A3, D7).
  - Loops use the service only once `decider_healthy` succeeds. Until then, every decision is skipped.
  - **Auto-start headroom (eng review TD3, D13):** `decider_start_once` auto-starts only when `ram_mb - docker_mem_mb >= 6144` (decider plus embedding model plus headroom), unless `CHALK_DECIDER=on` is set explicitly. Otherwise it warns once and the run proceeds as `off`.
  - **Idle shutdown (eng review TD2, D12):** the decider and chalk-embed exit after `CHALK_DECIDER_IDLE_MINUTES` (default 30) without a request, freeing their roughly 4 GB, and release their pidfiles. `decider_start_once` restarts them on demand. Tests cover idle exit (short timeout) and restart on the next run.
- **The per-loop time budget is 2 s** for all host-service calls combined. Each call gets `curl --max-time` set to whatever remains; when the budget runs out, the remaining calls are skipped. Any error or timeout means "no answer", which behaves like `off`.
- **The gray-zone stuck question**, asked only for `spinning` and `other` loops:
  - A single `noul` over the baseline's and the current E and T, plus a diff between their two trees (`git diff <baseline_tree> <tree>`), truncated to fit the model's context: "Is the agent stuck on the same root cause as the previous loop?"
  - In `on` mode, "yes" at ≥ `CHALK_DECIDER_THRESHOLD` (default 0.9) sends the run to detention immediately. It never extends a run.
- **Semantic recall**, which needs PR 3a:
  - `lessons` gains `embedding vector(<dim>)` with an **HNSW** index, `USING hnsw (embedding vector_cosine_ops)`.
  - Embeddings are written when a lesson is resolved. `chalk decider up` backfills existing ones.
  - Each query sets `SET LOCAL hnsw.ef_search = 100` and orders by `embedding <=> $q`, which matches `vector_cosine_ops`. On small tables the planner chooses an exact sequential scan; as the table grows, the index takes over (eng review S1, D3).
  - Semantic recall runs after the lexical step. Candidates from both are merged into the rerank shortlist.
- **The rerank:**
  - Enabled once resolved lessons reach `CHALK_DECIDER_MIN_LESSONS` (default 30); semantic recall uses the same gate.
  - It takes a shortlist of 8 (lexical and semantic, deduplicated) and asks one `noul` per lesson in a single batched request, keeping those at or above the threshold.
  - Exact fingerprint matches are always kept and come first.
- **Storage:** a `decisions` table with `call_id` (references `runs.id` of the loop call), `run_id`, `kind`, `question`, `answer`, `confidence`, `mode`, `latency_ms`, `acted` and `created_at`. The ledger gains a column for the decider.
- **Tests:** a fake host service that returns scripted answers and fixed vectors. The e2e cases cover:
  - the service being down;
  - timeouts and an exhausted budget;
  - low confidence;
  - shadow mode versus `on` mode;
  - `CHALK_FP_RULES=off` with the decider on;
  - a pg16 database (semantic recall skipped).

## Open Questions

1. **Is one repeat enough to detain on?** Decide from the PR 1 ledger.
2. **The decider's size and licence.** The model download is probably about 4 GB, and the licence of the Qwen3.5-2B base needs checking before Chalk documents installing it.
3. **Context limits.** What context length does the decider accept? The diff truncation rule depends on it.
4. **Which embedding model.** Pick one that runs on MLX and CPU with a permissive licence, and pin its dimension, since the `vector(<dim>)` column depends on it.
5. **Latency off Apple silicon.** CPU-only latency on Linux hosts is unmeasured. If loops regularly exhaust the 2 s budget, should `up` warn, or refuse?
6. **Ordering.** Should PR 3a ship before PR 2, so the database upgrade lands early while the table is still small?

## Success Criteria

- PR 1:
  - Every non-progress loop has exactly one verdict from {`blocked`, `agent_error`, `first`, `deja_vu`, `repeat`, `no_change`, `improving`, `spinning`, `other`}.
  - The ledger shows savings, false stops and converging-but-detained runs per `run_id`.
  - `make check` passes with every fixture listed above.
- **The bar for `CHALK_FP_RULES=on`:** after at least 20 detained runs in shadow mode, the stopping verdicts would have saved **≥ 20% of no-progress spend on detained runs**, with **at most 1 false stop**.
- PR 2:
  - No Hindsight code paths remain, and old config loads with a warning.
  - Older lessons are still recalled through the fallbacks.
  - **Regression contract (eng review T1, D10):** a resolved lesson that matches the current failure appears in prompt.md `<lessons>` and is counted in `runs.lessons`. Proven under `make test-db` against real Postgres for exact fingerprint, lexical first_error, legacy signature fallback, first-loop word_similarity, and no match. This replaces Hindsight e2e section 4.
  - First-loop recall returns lessons for a spec fixture that mentions a known failure.
  - Lessons-injected-then-progressed is no worse than before, over at least 20 loops.
- PR 3a:
  - Upgrading a pg16 fixture volume keeps every row.
  - A run on an un-upgraded pg16 database works, with a single warning.
- PR 3b:
  - With the service down, uninstalled or timing out, runs behave exactly as with `CHALK_DECIDER=off` (e2e test).
  - No loop spends more than 2 s on host-service calls.
  - Median `decisions.latency_ms` is under 500 ms on Apple silicon.

### R2-1 — feasibility

**Problem**

> D hashes the whole working tree, including specs/<TICKET>.notes.md. The retry prompt (share/prompts/retry.md step 5) tells the agent to record the cause and fix in that notes file on every retry. A stuck agent that follows instructions changes D on every loop, so `repeat` and `no_change`, the verdicts behind the headline savings, will rarely fire. The ledger would then under-report savings and the bar for `on` would never be met.

**Remedy**

> Exclude the notes file (and any other files Chalk asks the agent to touch every loop) from D, e.g. with a pathspec `:(exclude)specs/*.notes.md`, and add a fixture where only the notes file changes (expect the same D).

### R2-2 — completeness

**Problem**

> D is `git diff --cached $RUN_BASE`, but RUN_BASE moves. On a rubric-passed-no-tick loop run.sh commits and run_sync resets RUN_BASE to the new HEAD (run.sh:346-347, 137). The design doesn't say whether D is taken before or after that commit. If after, D is always the empty diff, so every second passed-no-tick loop is `no_change` even when the agent did work. If before, consecutive Ds are diffs against different bases and are not comparable: an agent that changes nothing after a committed loop gets a D that differs from the previous one, so `other` instead of `no_change`. The same problem affects a failing loop that follows a passed-no-tick loop in the same streak.

**Remedy**

> Define D as a base-independent tree identity, e.g. the `git write-tree` of the throwaway index, taken before any commit. 'Unchanged' then means the same tree as the previous loop in the streak. Add a fixture with two passed-no-tick loops in a row.

**Problem**
